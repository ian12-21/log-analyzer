## Step 4 – Analysis

- `loganalyzer/analysis.py`: a `Stats` class filled one event at a time with `add()`, so the same code works for a whole log and later for the live stream (Step 9). `summarize(events)` is a thin wrapper that feeds a list into a new `Stats`.
- Everything is counted with `collections.Counter`; pandas would be overkill here.
- Totals: `failed` and `accepted`, both weighted by `count` (a `message repeated N times` line counts as N).
- `top_ips()`, `top_users()` – failed attempts only; a successful login does not push an IP up the list.
- `top_invalid_users()` – names that do not exist on the system, from `Invalid user` lines. They are not added to `failed`, because the same attempt already has its own `Failed password for invalid user` line.
- `hourly_series()` – every hour from the first to the last failed attempt, including hours with zero, so the chart in the TUI has no gaps.
- Deviation from the guide: the guide counts `accepted += 1`; the code uses `count` for consistency with `failed`.
- `tests/test_analysis.py`: 9 tests (repeated count, invalid user not counted as failed, top lists, accepted not in top IPs, zero-filled hours, `add()` one by one equals `summarize()`, empty stats, both sample files). All 23 tests pass.

## Findings

- The parser counts lines (20 failed events in `sample_auth.log`), while Stats counts attempts (22). The difference is exactly the `message repeated` lines, so both numbers are correct and the README/defense should say which one is meant.
